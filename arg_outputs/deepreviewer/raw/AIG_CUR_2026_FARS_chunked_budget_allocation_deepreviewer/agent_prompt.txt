- After each paper_search call, update a running comparison matrix (internal reasoning artifact):
  [paper] | [task/setting] | [assumptions] | [method core] | [evidence strength] | [difference vs manuscript] | [implication for contribution].
- Use this matrix to identify the manuscript's true core value (what is genuinely new vs incremental) and to avoid inflated contribution claims.
- **STOP CRITERION — MARGINAL EVIDENCE GAIN:** if two consecutive retrieval bundles add no decision-relevant evidence (or add <=1 new directly relevant paper each), stop further retrieval and move to synthesis.
- Define paper_search failure as either (a) tool error or (b) zero usable returned papers.
- Track consecutive paper_search failures during this run.
- If two consecutive failures occur, enter Retrieval-Disabled Mode for the rest of the run:
  (1) stop calling paper_search,
  (2) do not output external paper links/URLs/arXiv IDs,

Sequential sweep protocol (mandatory):

Hardline defect-to-repair pipeline (must execute for every substantive paragraph):
Phase 1 — Defect discovery:
- Identify explicit defects, especially key factual errors, logical breaks, unsupported claims, and misleading wording.
- Classify as critical/major/minor based on impact to validity.
Phase 2 — Evidence and mechanism:
- Cite exact span-level evidence and explain the failure mechanism (why this is wrong, not only that it is wrong).
- State the scientific consequence if unchanged (invalid conclusion, irreproducibility, overclaim, confusion).
Phase 3 — Concrete repair design:
- Provide exact modification actions: what to delete, what to add, what to rewrite, and where to place it.
- When helpful, provide copy-ready replacement text and/or minimal experiment design.
Phase 4 — Validation gate:
- Check that each proposed fix directly closes the diagnosed defect and is feasible for authors to execute.
- If fix is expensive, provide a cheaper but valid fallback.
Phase 5 — Traceability:
- Ensure one-to-one mapping: defect -> evidence -> fix -> expected benefit.

Deep-review mandatory cognitive protocol (must run continuously, not once):
- Before final report drafting, build a one-page `Claim -> Evidence -> Warrant` map:
  (a) Claim: one-sentence ultimate thesis to be believed.
  (b) Key Results: 2-4 results that carry the claim.
  (c) Evidence: data/experiment/model output supporting each result.
  (d) Warrant: inference rule from evidence to conclusion (significance, mechanism, causal identification, theory deduction).
- Edge-removal stress test (mandatory): ask `if one edge in this map is removed, does the conclusion still stand?`.
  Any edge that collapses the conclusion is a priority audit target.
- Opponent-model reading (mandatory): read as if the paper is wrong first.
  For every key discussion/conclusion, ask:
  (a) Is there a simpler/common alternative explanation?
  (b) Is this explanation merely plausible language without discriminative verification?
  (c) Are there known conflicts/counterexamples in literature?
  (d) Is correlation written as causation, or local validity written as universal validity?
  (e) What other conditions could produce the same observation?
- Evidence-strength grading (mandatory for each key conclusion):
  Level 1 descriptive correlation/trend/case evidence;
  Level 2 quasi-experimental/causal-identification evidence;
  Level 3 randomized/strongly controlled evidence;
  Level 4 mechanism directly measured/validated.
- Check `evidence-level vs claim-level` mismatch (no level-jump over-claiming).
- Reproducibility audit (mandatory): judge if text alone can be reproduced.
  Verify data source/inclusion-exclusion, variable construction/preprocessing/missing-value handling,
  model and experiment hyperparameters, metrics/loss/evaluation consistency, and hidden dark-box steps.
- Traceability hard rule: any result-affecting choice must be traceable; non-traceable choices are high-risk.
- Anti-fragility robustness audit (mandatory): reason whether conclusions survive reasonable perturbations
  (settings, metrics/thresholds, subgroup consistency, multiple-testing/selective-reporting, effect-size vs practical significance, visual-misleading plots).
- Core robustness question: is the conclusion data-inevitable, or author-choice-accidental?
- Causal-language chain audit (mandatory when causal words appear):
  identify assumptions -> check support tests -> infer bias direction if assumptions fail.
- Mechanism distinguishability audit (mandatory): mechanism must produce falsifiable observable predictions,
  must be tested by data, and must be separated from plausible alternative mechanisms.
- Contribution-boundary audit (mandatory): decide the minimum publishable unit after removing packaging,
  and test whether external validity boundaries are honestly stated.
- Reader-path test (mandatory): verify closed loop `Intro problem -> Method answer -> Results evidence -> Discussion interpretation -> Conclusion bounded claim`.
  If this path cannot be reconstructed from title+abstract+figure captions+conclusion, mark structure/claim clarity risk.
- If any unresolved or newly discovered issue remains, continue using pdf_annotate for targeted annotation and re-check; do not finalize early.
- STEM/theory-heavy deep protocol (mandatory when formulas/theorems exist):
  (a) Formal abstract in <=10 lines: problem I/O/objective/assumptions, theorem-algorithm-empirical contributions,
      key conditions, SOTA advantage dimension, and failure modes.
  (b) Definition-Lemma-Theorem consistency audit: symbol identity card (type/dimension/domain/randomness/dependencies),
      hidden assumptions, quantifier consistency, and domain drift.
  (c) Proof skeleton verification: objective, major tools, and magic jump checks (tool applicability + rate/constant + boundary cases).
  (d) Literature comparability audit: stronger claims under stronger assumptions must be explicitly disclosed.
- ML/empirical deep protocol (mandatory):
  (a) Implementability check from text only (pseudo-code feasibility, critical hyperparameters, hidden engineering tricks).
  (b) Experiment tri-audit: fairness (budget/data/baseline parity), sufficiency (claim-aligned metrics + ablations + failure cases),
      statistics (multi-seed/variance/CI/significance/cherry-picking risk).
  (c) Metric alignment audit: ensure metrics truly measure target claims.
  (d) Theory-empirical closure audit: theorem algorithm and experimental algorithm differences must be explained and bounded.
- Constructive-advice contract (mandatory in final report and annotations):
  evaluate publishability, not author ability; critique gaps in text/method/evidence, not people.
  prefer minimum viable revision path over unrealistic full rewrite requests.
- Issue writing structure (mandatory per major item): `Problem -> Cause -> Actionable Fix -> Acceptance Criteria`.
- Requirement split (mandatory): label each requested action as `Must` (publication-critical) or `Nice-to-have` (quality improvement).
- Tone guardrail (mandatory): firm but non-attacking phrasing, e.g., `reader cannot verify yet` + concrete path to make it verifiable.
- Continuous-thinking rule (mandatory): all above checks must be actively maintained during every page and every step, not deferred to final summary only.

Objectivity and factuality audit (mandatory):
- For each major claim, run claim-evidence alignment and assign one label:
  [Proven] directly supported by reported experiments/derivations.
  [Partially proven] some support exists but key controls/tests are missing.
  [Unsupported] no direct evidence appears in current manuscript.
- If claim is partially proven or unsupported, annotation must include:
  (1) missing evidence type (ablation, control, statistics, OOD test, theoretical assumption),
  (2) scientific risk of current wording,
  (3) safer replacement wording.
- Causal-language rule:
  if no causal identification/control exists, avoid 'proves/causes/demonstrates'; use 'suggests/is consistent with'.
- SOTA-language rule:
  if settings are not strictly comparable, avoid global SOTA wording; use bounded comparative wording.
- First-claim policy:
  scoped 'first' claims are allowed when qualifiers are precise enough (task/setting/data regime/constraints/time scope) and related-work evidence is verifiable.
  if evidence is sufficient, explicitly acknowledge the claim as valid first-within-scope; do not force downgrade.
  if evidence is incomplete, request tighter qualifiers or downgrade wording to 'to our knowledge' until verified.
- Significance rule:
  if no variance/significance tests exist, avoid certainty wording on small margins.
- Scope rule:
  do not generalize beyond tested datasets/tasks/populations.

Claim rewrite templates for unsupported statements:
- Overclaim: 'Our method proves robust generalization to real-world deployment.'
- Better: 'Our method improves performance on evaluated benchmarks; real-world generalization needs dedicated OOD validation.'
- Overclaim: 'This module is the key reason for all gains.'
- Better: 'Results are consistent with this module contributing to gains, but causal attribution requires matched ablations.'
- Overclaim: 'We achieve state-of-the-art across settings.'
- Better: 'We outperform selected baselines under reported settings; broader SOTA claims require standardized cross-paper comparisons.'

Abstract paragraph/sentence guidance (4.1):
- Target compact 4-5 sentence structure:
  S1 problem and domain,
  S2 significance/challenge,
  S3 prior work limitation/gap,
  S4 proposed method,
  S5 (optional) key result and bounded implication.
- Keep abstract self-contained: no references, no deferred definitions, no citation placeholders.
- If a role is missing, propose concrete insertion/rewrite text to fill the missing role.
- Treat abstract as final-polish section: suggest concise end-stage rewrite when needed.

Introduction paragraph guidance (4.2):
- Introduction is the paper facade and should be around one page with clear paragraph roles.
- It must clearly answer three core questions:
  (1) what core problem is solved,
  (2) what solution is proposed,
  (3) what contributions are made.
- Also ensure narrative covers: problem -> idea -> method -> evidence/result preview.
- Contribution statements must be explicit, objective, and non-hyped.
- Replace vague modifiers (e.g., 'very clever', 'really cool') with concrete novelty statements.
- For each intro paragraph, provide exact revision path, including sentence-level replacements when useful.

Related work paragraph guidance (4.3):
- Do not write paper-by-paper chronological list-style summaries; organize by categories or comparison axes.
- Each related-work paragraph should state: category scope -> representative methods -> limitation/gap -> relation to this paper.
- Explicitly explain how this paper differs from strongest prior work.
- If comparison is weak, request concrete missing citations and specify comparison dimension.

Method paragraph guidance (4.4):
- Idea-first rule: explain intuitive mechanism before dense formulas.
- Avoid formula dump at opening; first convince reader of basic idea in plain language.
- Use top-down organization: overall framework first, then subsection details, then component internals.
- For equations: define symbols consistently, avoid notation conflicts, and map each equation to narrative purpose.
- For every key equation, verify objective direction/sign conventions, variable domains, tensor shapes/dimensions, normalization constraints, and boundary/assumption compatibility.
- Check consistency between equation statements and algorithm text/pseudocode/implementation description; flag mismatches explicitly.
- If clarity is low, propose examples/analogies and concrete structural rewrites.
- Enforce macro-to-micro flow (from whole system to parts), not reverse disclosure.

Experiment paragraph guidance (4.5 extension):
- Ensure experiments are claim-driven: each core claim has direct validation evidence.
- Require fair comparison setup (datasets, splits, budgets, baselines) and explicit reporting.
- Require ablation/composition checks when method contains multiple factors/components.
- Each result paragraph must include: observed result -> why it occurs -> what it implies -> plausible alternatives/limits.

Conclusion paragraph guidance (4.6):
- Keep conclusion shorter than abstract; recap completed validated work only.
- Use reader-switch check: rewrite from reader perspective, not author memory.
- Recommend concise structure: validated findings -> bounded limitations -> next actionable work.
- Do not introduce new unsupported claims in conclusion.

Scientific writing style protocol (05/06):
- Plain and straight-forward style only; avoid decorative or promotional language.
- Economy: use fewer words for same meaning; remove unnecessary dressing and repetition.
- Objective: factual, evidence-grounded, no speculation inflation.

Paper audit checklist (must systematically inspect):
A. Problem formulation
- Is the task definition precise, testable, and aligned with the claimed contribution?
- Are key assumptions explicit, justified, and realistic?
B. Novelty and related work
- Are novelty claims actually novel versus strongest relevant baselines?
- Are missing citations likely to change novelty interpretation?
C. Methodological soundness
- Are algorithm steps complete enough to reproduce?
- Are there hidden implementation tricks omitted from method description?
D. Mathematical consistency
- Check symbol reuse conflicts, undefined variables, dimensional mismatch, and unjustified approximations.
- Check whether claimed bound/derivation logically follows prior assumptions.
- Check equation-to-text consistency: optimization target, inequality direction, index range, and constraint definitions must match narrative descriptions.
- Check probability/calibration formulas for valid ranges and normalization (for example, sum-to-one, non-negativity, valid log inputs).
- Check loss definitions for missing coefficients/terms and sign mistakes that could invert optimization behavior.
- Moderation rule: prioritize key equations that can change conclusions; avoid exhaustive low-impact micro-corrections.
- Stop rule: once 1-2 high-confidence, evidence-backed corrections per affected key equation are established, stop expanding derivation branches and continue review.
E. Experimental validity
- Are baselines fair (same data split, preprocessing, tuning budget, model capacity)?
- Are ablations sufficient to support causal claims about each module?
- Are statistics complete (variance, confidence intervals, significance tests)?
F. Data and leakage risk
- Any train-test leakage, benchmark contamination, or selection bias?
- Any data curation choice that inflates reported performance?
G. Robustness and generalization
- Are stress tests, OOD tests, or failure-case analyses missing?
- Are limitations and threat models realistically scoped?
H. Efficiency and practicality
- Are compute/memory/latency costs reported and compared fairly?
- Is method deployment feasibility overstated?
I. Defensive writing and scientific claims
- Detect overconfident wording unsupported by evidence.
- Detect ambiguous phrasing that weakens falsifiability.
- Ensure claims are bounded by experimental evidence.
J. Presentation quality
- Identify paragraph-level logic breaks, typo-heavy fragments, and inconsistent terminology.
- For figure display/rendering and formatting anomalies, use cautious wording unless it is an obvious typo: mark as potential issue and ask authors to verify.
- Propose concrete rewrite text when useful.
K. Storyline and narrative quality
- Check whether title communicates problem focus, method identity, and practical value without exaggeration.
- Check whether key paragraphs follow a clear arc: motivation -> gap -> idea -> evidence -> implication.
- Check whether each paragraph has one clear role and avoids mixed, confusing intent.
- Propose concrete rewrites that improve readability and engagement while preserving scientific rigor.
L. Major-first then detail-level review order
- First settle major quality risks (research question/value/novelty/motivation-method alignment/validity/evidence sufficiency/over-claiming), then inspect detail-level defects.

## 1 INTRODUCTION

World models that predict environment dynamics have emerged as a powerful tool for agent decision-making (Ha & Schmidhuber, 2018; Schrittwieser et al., 2019). For agents operating in environments with irreversible actions—such as submitting purchases, sending emails, or deleting files—world models can serve as pre-execution verifiers: before committing to a high-stakes action, the agent queries the world model to predict whether the action will succeed. Recent work has demonstrated this approach for web agents, using LLM-based world models to verify checkout actions before execution (Li et al., 2025; Gu et al., 2025).

However, a counterintuitive failure mode has been observed: increasing the verification budget (the number of world-model queries allowed) can reduce task success rates (Li et al., 2025). This nonmonotonic behavior occurs because sequential verify-and-retry creates a problematic feedback loop. When verification rejects a checkout (potentially a false negative), the agent re-browses to find another product. During re-browsing, the agent often selects a worse product than the one originally found—a phenomenon we call trajectory drift. More verification cycles mean more opportunities for trajectory drift.

The key insight is that the problem lies not in verification accuracy, but in the sequential structure of verify-and-retry. Each rejection triggers re-browsing, compounding errors across cycles. This suggests a simple solution: instead of spreading the verification budget across many sequential cycles, spend it in fewer cycles with more parallel rollouts per cycle.

We propose chunked budget allocation: given a fixed verification budget B, allocate it across M cycles with K = B/M parallel world-model rollouts per cycle. By setting M = 1, we spend the entire budget in one parallel chunk, eliminating the sequential cycles that trigger trajectory drift. Our contributions are:

• We identify trajectory drift as the dominant failure mode in sequential verify-and-retry, accounting for 60.5% of failures when agents re-browse after verification rejection.  
• We demonstrate that chunked budget allocation achieves a 25× improvement in task success rate (21.50% vs. 0.86%) by eliminating sequential verification cycles.  
• We show that consensus aggregation across parallel rollouts provides no benefit over singlerollout acceptance, as the world model’s poor calibration (predicting pˆ = 0 for 98.4% of cycles) causes consensus to degenerate.  
• We provide practical guidance: setting M = 1 (spending all budget in one parallel chunk) consistently outperforms finer-grained allocations, with performance degrading monotonically as M increases.

## 3 METHOD

## 3.1 PROBLEM SETUP

We study world-model verification for irreversible actions in the WebShop environment (Yao et al., 2022), a text-based e-commerce benchmark where an agent must navigate product search and complete purchases. The agent receives text observations describing search results and product pages, and takes actions such as searching, clicking products, and checking out. Checkout is an irreversible action: once executed, the episode terminates regardless of whether the purchase matches the user’s intent.

Our setup uses Gemini-2.5-Flash as the acting agent and a fine-tuned Qwen2.5-7B model as the world model (Li et al., 2025). Given the current trajectory history h and a candidate action $^ { a , }$ the world model predicts the next observation $s ^ { \prime }$ and a binary success indicator $R ^ { \prime } \in \{ 0 , 1 \}$ . For checkout verification, R′ indicates whether the purchase would satisfy the user’s intent.

## 3.2 VERIFICATION FRAMEWORK

Given a verification budget B (maximum world-model calls per episode), we consider how to allocate this budget across M verification cycles, with $K = B / \dot { M }$ parallel rollouts per cycle. When the agent proposes checkout, we generate K independent stochastic world-model predictions from the current state and compute the consensus estimate:

$$
\hat {p} = \frac {1}{K} \sum_ {k = 1} ^ {K} \mathbb {1} [ R _ {k} ^ {\prime} = 1 ] \tag {1}
$$

The checkout proceeds if $\hat { p } \geq \tau$ (threshold), otherwise it is blocked and the agent continues browsing. After M cycles, any subsequent checkout attempt automatically passes (budget exhausted).

## 3.3 EXPERIMENTAL CONDITIONS

We compare three verification strategies at the same budget $B = 1 0 !$

Condition A (Sequential Verify-and-Retry). The standard approach from prior work (Li et al., 2025): each checkout proposal triggers a single world-model query $( K = 1 )$ . If $R ^ { \prime } = 1$ , checkout proceeds; if $R ^ { \prime } = 0$ , checkout is blocked and the agent continues. This allows up to M ≈ 10 verification cycles.

Condition B (Chunked Consensus). Our proposed approach: spend the entire budget in $M = 1$ cycle with $K = 1 0$ parallel rollouts. Checkout proceeds if $\hat { p } \geq \tau$ (we use $\tau = 0 . 1 )$ . This eliminates sequential verification cycles that could trigger trajectory drift.

Condition C (Chunked No-Aggregation). A control condition with the same structure as B (M = 1, K = 10) but without consensus aggregation: only the first rollout’s R′ determines the decision. This isolates whether gains come from reducing cycles (shared by B and C) or from consensus aggregation (only in B).

## 4.6 WHY CONSENSUS AGGREGATION FAILS

The world model is poorly calibrated as a confidence estimator. Across 311 verification cycles in Condition B, the consensus estimate $\hat { p } = 0 . 0$ for 98.4% of cycles (306/311), with Brier score 0.28 and expected calibration error (ECE) 0.28. When $\hat { p } = 0 . 0$ , the actual success rate is 27.5% (84/306 successes)—far from the predicted 0%. The rare cases where $\hat { p } > 0$ (only 5 cycles) all resulted in success, but the sample size is too small for reliable conclusions.

This extreme concentration of predictions at $\hat { p } = 0 . 0$ explains why consensus aggregation does not help: when all K rollouts predict failure, majority voting cannot recover the correct answer. The benefit of chunked verification comes entirely from the structural change (fewer sequential cycles), not from the aggregation rule. For practitioners, this suggests that when using poorly-calibrated world models, the priority should be minimizing sequential verification cycles rather than investing in sophisticated aggregation schemes.

## 5 CONCLUSION

We studied how to allocate a fixed verification budget when using world models to verify irreversible actions. Our key finding is that budget allocation structure matters more than aggregation sophistication: chunked verification (M = 1, spending all budget in one parallel chunk) achieves 25× improvement over sequential verify-and-retry at the same budget, primarily by avoiding trajectory drift—the dominant failure mode where rejected checkouts trigger agent re-browsing that leads to worse product selections.

Our work has limitations: we evaluate on a single domain (WebShop) with a single world model (Qwen2.5-7B), and absolute success rates remain modest (21.50%). Future work should investigate whether these findings generalize to other domains with irreversible actions, explore bettercalibrated world models that could benefit from consensus aggregation, and develop adaptive budget allocation strategies that adjust M based on task difficulty.
