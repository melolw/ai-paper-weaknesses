1) Summary
The paper addresses the limitation of existing remasking strategies in diffusion language models for code generation, which rely on model-internal signals rather than semantic error localization. The authors propose execution-trace guided remasking, an inference-time method that parses exception tracebacks or collects line-level execution traces to identify failure-relevant code regions. These regions are mapped to token indices and selectively remasked for conditional diffusion repair. Evaluated on MBPP+ and HumanEval+ using LLaDA-8B-Base, the method achieves 31.22% pass@1 on MBPP+, significantly outperforming no-repair and CORE baselines. Ablations and analysis demonstrate that trace-guided localization enables meaningful code modifications, whereas global low-confidence remasking rarely alters generated code.2) Strengths
- **Novel Integration of Execution Feedback with Diffusion Remasking**
  - Bridges execution-guided debugging (Section 2) with diffusion's native remasking capability, offering a semantically grounded alternative to confidence-based heuristics (Section 1). This matters for novelty as it introduces a new paradigm for inference-time scaling that leverages runtime diagnostics rather than internal model uncertainty.
  - Hierarchical localization strategy (Section 3.3) effectively handles both exception tracebacks and assertion failures, covering the majority of failing cases (Figure 2). This matters for technical soundness as it ensures robust failure localization across different error manifestations.
  - Enables targeted repair without full regeneration, preserving correct code structure while fixing localized bugs (Section 3.4). This matters for impact as it reduces unnecessary computational waste and maintains syntactic coherence in generated programs.
- **Rigorous Experimental Evaluation and Baselines**
  - Uses a strict 20/80 feedback/evaluation test split to prevent leakage (Section 4.1), ensuring repair decisions are not overfitted to evaluation tests. This matters for experimental rigor as it isolates the true generalization capability of the repair mechanism.
  - Compares against multiple relevant baselines including CORE and Best-of-2 under matched compute budgets (Table 1), isolating the benefit of semantic guidance. This matters for technical soundness as it rules out trivial explanations like increased compute or sampling diversity.
  - Reports statistical significance via McNemar test ($p < 0.001$) and averages over 3 seeds (Section 4.3), strengthening result reliability. This matters for experimental rigor as it provides statistically validated evidence of performance gains.
- **Insightful Diagnostic Analysis**
  - Edit locality analysis (Figure 3) quantitatively shows trace-guided repair makes substantial changes (mean edit distance 10.01) vs. low-confidence repair (0.95), explaining performance gaps. This matters for clarity and impact as it provides a mechanistic explanation for why semantic localization outperforms confidence-based heuristics.
  - Error-type breakdown (Table 3) reveals differential success rates across syntax, runtime, and assertion errors, highlighting method strengths and limitations. This matters for technical soundness as it demonstrates nuanced understanding of where the method excels and where it struggles.
  - Ablation on localization window size and repair steps (Table 2) provides actionable hyperparameter insights, showing broader context ($\pm 5$ lines) improves performance. This matters for experimental rigor as it systematically validates design choices and guides future implementations.3) Weaknesses
- **Limited Generalization to Complex Benchmarks**
  - Performance on HumanEval+ remains very low (2.64% pass@1, Table 1), indicating the method struggles with more complex or abstract problems where execution traces may be sparse or misleading. This matters for technical soundness as it suggests the approach may not scale to harder code generation tasks.
  - The reliance on Python-specific tracing (`sys.settrace`, Section 3.3) limits applicability to other programming languages without significant adaptation. This matters for impact as it restricts the method's immediate utility in polyglot or non-Python development environments.
  - No evaluation on multi-file or module-level code generation, where traceback parsing and line mapping become non-trivial (Section 3.4 mentions mapping lines to tokens but assumes single-file context). This matters for experimental rigor as it leaves open questions about real-world deployment in larger codebases.
- **Compute and Latency Overhead Not Fully Quantified**
  - The method requires multiple execution runs and up to 3 repair rounds, increasing NFE to 294 (Table 1), but wall-clock time and GPU memory overhead are not reported. This matters for experimental rigor as NFE alone does not capture the true computational cost of execution tracing and iterative repair.
  - Line tracing via `sys.settrace` introduces runtime overhead during test execution, which is acknowledged but not measured (Section 4.1 mentions timeout but not tracing cost). This matters for technical soundness as unquantified tracing latency could negate efficiency gains in time-sensitive applications.
  - The iterative repair loop may fail to converge for cascading errors, yet the paper lacks analysis on convergence rates or maximum effective rounds beyond the fixed $R_{max}=3$ (Section 3.4). This matters for clarity and impact as it leaves the stopping criterion and convergence behavior empirically unvalidated.
- **Ambiguity in Token Mapping and Masking Strategy**
  - The mapping from source lines to token indices (Section 3.4) assumes a direct correspondence, but tokenization artifacts (e.g., whitespace, comments, multi-line strings) could misalign spans. This matters for technical soundness as misaligned token masks could corrupt syntactically valid regions or miss the actual bug.
  - The fallback to global low-confidence repair when localization fails (Section 3.3) is not analyzed in depth, despite covering ~5-7% of cases (Figure 2). This matters for experimental rigor as the fallback mechanism's effectiveness and failure modes remain uncharacterized.
  - The repair temperature $\tau=0.2$ and step count $S=64$ are fixed; sensitivity analysis or adaptive scheduling for these parameters is missing (Section 4.1, Appendix A). This matters for clarity and technical soundness as fixed hyperparameters may not generalize across different error severities or model scales.
- **Experimental Consistency and Baseline Configuration Issues**
  - A significant NFE discrepancy exists between the main results and ablation study: Table 1 reports an average NFE of 294 for the trace-guided method, while Table 2 reports 154 for the identical "Full Method" on the same benchmark. This matters for experimental rigor as the unexplained ~48% variance undermines compute budget transparency.
  - The global low-confidence baseline uses fewer repair steps ($S=32$) than the proposed method ($S=64$), as stated in Section 4.2. This matters for technical soundness as asymmetric compute allocation can artificially inflate the relative advantage of the proposed approach.
  - Localization statistics exhibit a denominator mismatch: the table in Section 4.5 reports percentages out of the total benchmark size (e.g., 41.0% exception-based), while the accompanying text reports percentages out of failing problems only (e.g., 51.5%). This matters for clarity as it creates superficial numerical contradictions without explicit clarification.
  - The citation year for the CORE baseline conflicts between Section 1 (2026) and Section 4.2 (2024). This matters for presentation rigor as inconsistent referencing undermines reference accuracy.4) Suggestions for Improvement
- **Expand Evaluation Scope and Language Support**
  - Include evaluation on additional benchmarks with varying complexity (e.g., APPS, MultiPL-E) to assess scalability beyond MBPP+ and HumanEval+ (Section 4.1).
  - Provide a language-agnostic localization interface or demonstrate adaptation to at least one non-Python language to validate cross-language feasibility beyond the Python-specific tracer (Section 3.3).
  - Test on multi-file projects or modular code generation tasks to evaluate traceback parsing and token mapping robustness in realistic development settings (Section 3.4).
- **Quantify Computational Costs and Convergence Behavior**
  - Report wall-clock latency, GPU memory usage, and tracing overhead per repair round to provide a complete compute-efficiency profile alongside NFE metrics (Table 1).
  - Analyze convergence statistics across repair rounds (e.g., percentage of problems fixed at round 1 vs. 2 vs. 3) to justify the $R_{max}=3$ choice and identify diminishing returns (Section 3.4).
  - Compare against adaptive compute baselines that dynamically allocate repair steps based on error severity or localization confidence to contextualize the fixed-step approach (Section 4.1).
- **Refine Token Mapping and Masking Robustness**
  - Implement and evaluate a tokenization-aware span mapper that handles whitespace, comments, and multi-line constructs to reduce misalignment errors during line-to-token conversion (Section 3.4).
  - Conduct a dedicated analysis of fallback cases to identify failure modes of the localization strategy and propose targeted improvements for the ~5-7% of cases requiring global repair (Figure 2).
  - Perform sensitivity analysis on repair temperature and step count, or introduce an adaptive scheduling mechanism that adjusts $\tau$ and $S$ based on localization confidence or error type (Section 4.1, Appendix A).
- **Resolve Consistency Discrepancies and Standardize Baselines**
  - Clarify the NFE variance between Table 1 (294) and Table 2 (154) by reporting per-seed NFE averages or explaining early-stopping/seed-specific failure rate differences.
  - Align the compute budget for the global low-confidence baseline by using $S=64$ repair steps to match the proposed method, ensuring a fair comparison (Section 4.2).
  - Explicitly state the denominator used for localization statistics in both the table and text (e.g., clarify that table values are over total problems while text values are over failing problems) to eliminate numerical confusion (Section 4.5).
  - Standardize the CORE citation year across the manuscript and reference list to ensure bibliographic consistency (Sections 1 and 4.2).5) Score
- Overall (10): 7 — The method offers a novel and effective integration of execution feedback with diffusion remasking, demonstrating strong results on MBPP+ (Table 1), though limited HumanEval+ performance and unquantified compute overhead temper the overall impact.
- Novelty (10): 8 — Bridging runtime diagnostics with diffusion-based targeted repair is a conceptually clear and timely contribution (Section 3), extending execution-guided debugging to non-autoregressive paradigms.
- Technical Quality (10): 6 — The pipeline is well-designed and empirically validated with rigorous baselines and ablations (Tables 1-3), but requires correction of NFE discrepancies, baseline step asymmetry, and statistical denominator mismatches to fully meet reproducibility standards.
- Clarity (10): 8 — The manuscript is well-structured with clear methodological descriptions (Section 3) and informative figures (Figures 1-3), though some implementation details regarding token mapping and fallback handling could be more explicit.
- Confidence (5): 4 — High confidence based on clear experimental setup, reproducible code availability, and comprehensive ablation studies, though limited evaluation on complex benchmarks slightly reduces certainty about generalizability.
